# Remediation Plan for WorkshopsAI CMS


## 1. Verified Project Architecture


Recent inspection of the `workshopsAI_cms` repository shows that the application’s **frontend is built with Lit web‑components and not React**. The `main.ts` entry file imports `LitElement` and uses Vaadin’s router to define the client‑side routes【794849583437156†L0-L3】. A simplified entry point (`main-simple.ts`) exists which does not use Vaadin Router; it manually inspects `window.location.pathname` and renders components conditionally【699872676371748†L51-L66】. The project README also states that the frontend uses vanilla JavaScript and Web Components with Tailwind CSS【842279428743700†L80-L85】. The backend remains a Node.js/Express API with PostgreSQL, Drizzle ORM and comprehensive REST routes such as `src/routes/api/dashboard.ts`【476284415499611†L20-L27】 and questionnaire modules (`questionnaires.ts` and `questionnaires-new.ts`)【928293013961981†L0-L3】【273820021362802†L0-L8】.


### Frontend Observations


- **Routing:** Two entry points exist. `main.ts` uses Vaadin Router and renders pages as LitElement components【794849583437156†L0-L3】. `main-simple.ts` implements a custom router that checks the path and toggles between the login screen, registration screen and dashboard【699872676371748†L51-L66】. The dashboard sub‑routes are mostly unimplemented; any path other than `/dashboard` or `/dashboard/questionnaires/new` displays a “route not yet implemented” message【699872676371748†L174-L193】.
- **Dashboard metrics:** Both `main.ts` and `main-simple.ts` show hard‑coded zero values for metrics such as number of workshops, questionnaires and responses【699872676371748†L96-L121】. The backend exposes a `GET /api/dashboard/overview` endpoint【476284415499611†L20-L27】, but the frontend never calls it.
- **Authentication tokens:** The authentication service stores tokens under the key `workshopsai-access-token`【997578574722127†L194-L197】. However, the workshop API service reads `localStorage.getItem('auth_token')` and attaches this value to the `Authorization` header【702342811682397†L31-L35】. This mismatch prevents authenticated calls from succeeding.
- **Questionnaire endpoints:** There are two questionnaire API modules (`questionnaires.ts` and `questionnaires-new.ts`)【928293013961981†L0-L3】【273820021362802†L0-L8】. Their coexistence and mixed usage in the frontend lead to duplication and maintenance problems.
- **Workshop editor duplication:** Two similarly named components, `workshop-editor.ts`【200567878494766†L0-L8】 and `WorkshopEditor.ts`【400384249415102†L0-L8】, implement workshop editing. Both register the same custom element (`workshop-editor`). This duplication can confuse developers and cause inconsistent behaviour.

## 3. Phase 1 – Fix Critical Functional Bugs


### 3.1 Standardise Authentication Token Usage


- **Centralise token key.** Introduce a constant (e.g., `ACCESS_TOKEN_KEY = 'workshopsai-access-token'`) in a shared module. Replace all occurrences of `localStorage.getItem('auth_token')` with `localStorage.getItem(ACCESS_TOKEN_KEY)` and ensure all services (workshop, questionnaire, etc.) use the same helper functions for storing and retrieving tokens. This resolves the mismatch between `authService`【997578574722127†L194-L197】 and `workshopService`【702342811682397†L31-L35】.
- **Adjust interceptors.** Update Axios interceptors in `workshopService` and other API services to read the unified token. If a request receives a 401 response, the interceptor should clear the token and redirect the user to the login page.


### 3.2 Connect Dashboard to Live Data


- **Call the backend.** Replace the hard‑coded dashboard metrics in both routing modules with asynchronous calls to the `GET /api/dashboard/overview` endpoint【476284415499611†L20-L27】. Use the authenticated Axios instance (with the correct token) to fetch counts of workshops, questionnaires, responses and analysis jobs.
- **Add loading and error states.** Show a loading spinner while fetching metrics and display user‑friendly error messages if the API call fails.


### 3.3 Implement Workshop Creation Route


- **Handle `/dashboard/workshops/new` in the router.** In `main-simple.ts`, add a case for `/dashboard/workshops/new` that renders the workshop editor component. Do not leave unhandled sub‑routes falling back to the “route not yet implemented” message【699872676371748†L174-L193】.
- **Select a canonical workshop editor.** Decide whether to keep `workshop-editor.ts` or `WorkshopEditor.ts`. Both register the same custom element (`workshop-editor`)【200567878494766†L25-L26】【400384249415102†L37-L38】. Choose the version that is most up‑to‑date (for example, the one containing multi‑language support, step‑based editing and auto‑save features【400384249415102†L28-L35】). Remove or mark the other as legacy to avoid confusion.


## 4. Phase 2 – Architectural Consolidation


### 4.1 Choose a Single Client‑Side Router


- **Select one routing system.** Either adopt the Vaadin Router defined in `main.ts`【794849583437156†L0-L3】 or keep the custom router in `main‑simple.ts`【699872676371748†L51-L66】. The custom router is currently active and simpler to maintain, but Vaadin Router offers declarative route definitions and nested routing. Whichever option you choose, remove or deprecate the other. Update documentation to reflect the decision.


### 4.2 Unify Questionnaire API


- **Deprecate the old endpoint.** Decide whether `questionnaires-new.ts` should be the canonical implementation (it uses more descriptive property names and advanced validation【273820021362802†L0-L8】). Mark `questionnaires.ts` as legacy. Adjust frontend API calls to use only the selected version. Alternatively, implement API versioning (e.g., `/api/v1/questionnaires` and `/api/v2/questionnaires`) and migrate gradually.


### 4.3 Consolidate Workshop Editors


- **Remove duplication.** After selecting the preferred workshop editor component in Phase 1, delete the unused duplicate or mark it clearly as deprecated. Update imports across the project so that only one version is ever used. Document the editor’s responsibilities (step‑based editing, live preview, internationalisation) in the README.


### 4.4 Centralise API Base URL and Services


- **Create a unified API client.** Instead of each service creating its own Axios instance, define a central API client that sets the `baseURL`, attaches the token, handles refresh tokens and logs errors. This client can be imported across services, ensuring consistent behaviour. Document its usage in a new `API.md` file.


## 5. Phase 3 – Clean‑up Dead Code and Unused Features


- **Remove unused components.** Components such as `file-upload.ts` and unused services should be deleted or moved to a `deprecated/` directory. They currently have no routes or navigation linking to them and serve only to clutter the codebase.
- **Eliminate unused backend routes.** Modules like `email-integration.ts` that have no frontend counterparts should either be removed or fully implemented in the UI. Similarly, prune leftover route handlers and middleware that are never invoked.
- **Establish a deprecation policy.** Create a `LEGACY.md` file listing deprecated modules (e.g., `main.ts`, `questionnaires.ts`) and the timeframe for their removal. This provides transparency and prevents accidental reuse.


## 6. Phase 4 – Security and User‑Experience Improvements


- **Input validation.** Augment forms with robust client‑side validation and user feedback. Ensure that authentication and registration forms validate required fields before submission.
- **Error handling and loading states.** Provide clear error messages when API calls fail and use loading indicators to avoid confusing the user.
- **CSRF protection and secure storage.** Consider migrating token storage to HTTP‑only cookies or a more secure mechanism than localStorage. Implement CSRF tokens if forms perform state‑changing operations.
- **Consistent i18n.** The repository includes an internationalisation service (`services/i18n`). Ensure all new UI elements integrate with this service and support Polish and English.


## 7. Phase 5 – Documentation and Testing


- **Update README and docs.** Reflect the chosen routing system, API base paths and token handling strategy in the README. Add a `SECURITY_NOTES.md` describing how authentication works and how tokens are stored.
- **Expand the audit report.** Keep the `APPLICATION_FEATURES_AUDIT.md` up to date by adjusting statuses (e.g., `BROKEN` to `OK` when features are fixed). Document why a feature is considered `LEGACY` and when it will be removed.
- **Introduce tests.** Leverage the existing Playwright and Jest infrastructure. Write end‑to‑end tests for authentication, dashboard metrics retrieval and workshop creation. Add unit tests for critical services such as auth and workshop services. Use continuous integration scripts (`ci:test`, `ci:build`) to ensure that tests run automatically on every commit.


## Conclusion


The WorkshopsAI CMS repository contains a powerful backend but a front‑end that is still in transition. The remediation plan outlined above aims to bring the frontend in line with the backend’s capabilities while clarifying the architecture. The first priority is to **unify the authentication token and display real data on the dashboard**【699872676371748†L96-L121】【997578574722127†L194-L197】【702342811682397†L31-L35】.
